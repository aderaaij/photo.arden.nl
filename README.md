# photo.arden.nl

A photography portfolio that doubles as a WebGL showcase. A frontpage cover
carousel → WebGL transition → per-gallery scroll experience: magazine-style
layout, scroll-driven section colors pulled from the photos themselves, and
"trip" galleries that open on a stylized animated route map.

Everything is **drop-and-go from folders** — add photos, optionally annotate in
one config file, and it builds itself. The repo is the CMS for now (see
[Content](#content)); the data layer is isolated so it can move to a real CMS
later without touching the app.

## Stack

- **Vite + React + TypeScript** — SPA, fast WebGL dev loop
- **React Three Fiber + drei + postprocessing** — declarative Three.js
- **GSAP + Lenis** — animation + smooth scroll
- **GLSL** (`vite-plugin-glsl`) — the header / map / cover-reveal shaders
- **Zustand** — state shared across the React ↔ Canvas boundary
- **React Router** — shareable per-gallery URLs (`/g/<slug>`)
- **vite-imagetools** — build-time WebP resizing (the image pipeline)
- **sharp** — used by the build scripts (palettes, map geometry)

## Run

```bash
pnpm install
pnpm dev        # dev server
pnpm build      # typecheck + production build
pnpm preview    # preview the build
pnpm palettes   # regenerate photo-derived section colors (see below)
```

## Content

All gallery data flows through `src/lib/content.ts` (`getGalleries()` /
`getGallery()`) — the **only** module the app imports for content. Today it
reads repo files; to migrate to a CMS, swap those two function bodies and
nothing else changes.

### 1. A simple gallery

Drop images into `src/photos/<slug>/`. The folder name is the slug.

- `cover.*` becomes the gallery cover (else the first image)
- the rest become the gallery, **in filename order** (`01.jpg`, `02.jpg`, …)
- alt text is derived from the filename
- a folder with images but no config entry still appears, with a default theme

That's the whole minimum. Titles, intros, colors, etc. are optional metadata:

### 2. Gallery metadata — `src/content/galleries.config.ts`

```ts
{
  slug: 'coastal',                 // must match the folder name
  title: 'Coastal',
  intro: 'Atlantic light, salt, and long horizons.',
  theme: { bg: '#e9e4da', fg: '#1b1a17', accent: '#3d6e7a' },
}
```

Order in this array = order on the frontpage. `theme` is optional — without it,
the colors are derived from the photos (see [Section colors](#4-section-colors)).

### 3. Chaptered & trip galleries

A gallery becomes **chaptered** by using one more folder level:

```
src/photos/japan/
  cover.jpg
  01-tokyo/    20240203-DSCF2612.jpg  …
  02-sapporo/  …
  03-otaru/    …
```

- Chapters run in **folder order** (hence the numeric prefix).
- Each chapter becomes a **section** with its own header and its own background.
- The part after the numeric prefix (`tokyo`, `sapporo`) is the chapter **id**.

A **trip** gallery adds a `trip` block to its config entry — this turns on the
animated route map (assembles on load, draws a flight-in, then travels one leg
to each chapter as you scroll) and supplies each chapter's kanji/label:

```ts
{
  slug: 'japan',
  title: 'Japan',
  intro: 'Tokyo north to Hokkaido, then south to Kyushu.',
  trip: {
    stops: [
      // `id` matches the chapter folder (sans prefix). `label` heads the
      // chapter; `name` is the small romaji on the map. labelDir/theme optional.
      { id: 'tokyo',   label: '東京', name: 'Tokyo',   lon: 139.69, lat: 35.69 },
      { id: 'sapporo', label: '札幌', name: 'Sapporo', lon: 141.35, lat: 43.06 },
      { id: 'otaru',   label: '小樽', name: 'Otaru',   lon: 141.0,  lat: 43.19, labelDir: 'left' },
    ],
  },
}
```

The map outline is a generated file (`src/content/japan-geo.json`) — see
[Build scripts](#build-scripts) to make one for a different country.

Non-trip chaptered galleries can label chapters with a `chapters` map instead:
`chapters: { spring: 'Spring', summer: 'Summer' }`.

### 4. Section colors

Each section's background, text, and accent can come from two places, in order
of priority:

1. **Hand-authored** — a `theme` on the trip stop (or section), always wins.
2. **Photo-derived** — generated by `pnpm palettes` into
   `src/content/section-palettes.json`, used when there's no hand-authored theme.

The colors crossfade as you scroll from one chapter into the next (background,
text, map ink — all from one live palette).

**To make a chapter use its own photos' colors:** drop the real photos in,
delete that chapter's `theme:` line, and run `pnpm palettes`. The extractor
median-cuts each folder, picks a background from the most characterful
secondary color (a blazing red lantern beats a dull wall), and decides
light/dark from overall brightness so daytime chapters go airy and night
chapters go deep. Two dials live at the top of
`scripts/build-section-palettes.mjs`:

- `DARK_BG_L` — lightness of dark backgrounds (lower = moodier, higher = airier)
- `NIGHT_MAX_L` — the day/night threshold (brighter sets become light themes)

Re-run `pnpm palettes` whenever you add or change a chapter's photos.

### 5. Art direction — `layout.json`

By default the layout is automatic (see [below](#automatic-layout)). To **fully
art-direct** a chapter, drop a `layout.json` **beside its photos**
(`src/photos/japan/04-fukuoka/layout.json`). Photos are referenced by any
substring of their filename:

```json
[
  { "hero": "DSCF3606" },
  ["DSCF3374", "DSCF3388"],
  { "full": "DSCF3392" },
  ["DSCF3398", "DSCF3608", "DSCF3614"],
  { "photo": "DSCF3621", "place": "right" }
]
```

| entry | result |
| --- | --- |
| `"DSCF1234"` | a centered single |
| `["a", "b", "c"]` | a **row**, side by side (justified to equal height) |
| `{ "full": "x" }` | a full-bleed page |
| `{ "hero": "x" }` | a large opener |
| `{ "photo": "x", "place": "left"\|"right"\|"center"\|"full"\|"hero" }` | a single, placed |

Anything you **don't** list is appended afterward via the automatic layout, so
nothing disappears while you're arranging. Unknown filenames log a console
warning. Editing the file hot-reloads. Delete it to return the chapter to auto.

(For a flat, non-chaptered gallery, put `layout.json` at the gallery root:
`src/photos/<slug>/layout.json`.)

#### Automatic layout

With no `layout.json`, the engine builds a magazine cascade from photo order and
orientation: a hero opener, runs of consecutive **landscapes gathered into
justified rows of 2–3**, occasional full-bleed breaks, and portraits that pair
or stand alone. Frames always match each photo's real aspect ratio (from the
image pipeline), so **a portrait is never cropped into a landscape frame** or
vice versa. Ordering landscapes next to each other makes them cluster.

## Photos & the image pipeline

**Export masters at ~2560px on the long edge, quality ~90.** Originals live in
`src/photos/` as the source — they are **never served**. At build,
`vite-imagetools` resizes every image to WebP capped at **2560px long edge**
(`src/content/galleries.ts`) and the app serves those (~600 KB each, vs multi-MB
originals). It **never upscales**, so exporting below 2560 means soft full-screen
shots; exporting larger just gets downscaled to 2560.

- The served width/quality is one line in `galleries.ts` (`w/h/fit/quality`).
- `MAX_TEX` in `src/canvas/GalleryPhoto.tsx` caps GPU texture size (matched to 2560).
- Photo **dimensions** come from imagetools metadata automatically — no script
  needed; framing is always correct the moment you drop files in.

Keep your true full-resolution archive in your photo library, not the repo
(full-res masters bloat git for no runtime benefit).

## Build scripts

| script | when to run |
| --- | --- |
| `pnpm palettes` | after adding/changing a chapter's photos, to refresh photo-derived section colors → `src/content/section-palettes.json` |
| `node scripts/build-japan-geo.mjs` | to regenerate the trip map outline → `src/content/japan-geo.json` (edit the source country/region inside) |
| `node scripts/gen-placeholders.mjs` | to generate stand-in photos for empty chapters while you wait on real ones |

`section-palettes.json` and `japan-geo.json` are committed (generated artifacts).

## Architecture

- A single **persistent `<Canvas>`** lives in `Layout` and never unmounts, so
  transitions can span route changes. `SceneManager` swaps `IndexScene` /
  `GalleryScene` from the store.
- **Galleries are DOM-driven:** `GalleryPage` lays the photos out as invisible
  CSS-grid cells; `GalleryScene` mounts a textured plane per cell and snaps it to
  the cell's rect every frame. CSS owns layout + native (Lenis) scroll; WebGL
  owns rendering. Layout logic lives in `src/lib/domGallery.ts`.
- The Canvas sits **behind** a `pointer-events: none` DOM overlay; interactive
  elements opt back in.
- React context doesn't cross into the Canvas, so shared state (view, scroll,
  the live color palette, `navigate`) goes through the Zustand store / the
  `src/lib/palette.ts` module, read inside `useFrame` to avoid re-renders.

### Key files

```
src/
  content/galleries.config.ts   ← you edit: titles, themes, trips
  content/galleries.ts          ← auto-discovery (globs photos + layout.json)
  content/section-palettes.json ← generated by `pnpm palettes`
  content/japan-geo.json        ← generated map outline
  lib/content.ts                ← the content API (swap for a CMS later)
  lib/domGallery.ts             ← layout engine (auto + layout.json)
  lib/palette.ts                ← live scroll-driven color
  canvas/GalleryScene.tsx       ← per-cell planes + palette crossfade
  canvas/GalleryPhoto.tsx       ← cover-cropped photo plane
  canvas/TripMap.tsx            ← animated route map
  canvas/HeaderText.tsx         ← scroll-driven slice-reveal headers
  photos/<slug>/[NN-chapter/]   ← your photos (+ optional layout.json, cover.*)
```
